SakikoMind 智能客服系统测试报告
================================

一、测试目的
验证 SakikoMind 在真实大模型调用下的意图识别、Agent 路由、知识库检索和人工升级能力。

二、测试环境
- 运行方式：Docker Compose
- 基础环境：Windows + WSL 2 + Docker Desktop
- 后端入口：http://localhost:8000
- 接口文档：http://localhost:8000/docs
- 模型服务：DeepSeek Anthropic 兼容接口
- 已启动组件：SakikoMind API、Redis、ChromaDB、Prometheus、Nginx

三、测试结果

1. 普通咨询
   输入：你好，我想了解一下你们能提供哪些服务？
   结果：通过
   intent：query
   agent_type：general
   knowledge_used：true
   说明：系统正确识别普通咨询，并由通用客服 Agent 返回服务范围说明。

2. 退款申请
   输入：我想申请退款，应该怎么处理？
   结果：部分通过
   intent：request
   agent_type：general
   knowledge_used：true
   说明：回答正确给出了退款条件、审核和到账流程，但未按预期路由到 billing Agent。

3. 重复扣款
   输入：我的银行卡被重复扣款了，请帮我处理。
   结果：通过
   intent：billing
   agent_type：billing
   escalated：true
   knowledge_used：true
   说明：系统正确识别资金风险，要求订单号、交易时间、金额和支付渠道，并建议人工复核。

4. 登录认证失败
   输入：我无法登录账号，系统提示认证失败。
   结果：部分通过
   intent：account
   agent_type：technical
   escalated：true
   knowledge_used：true
   说明：主路由正确进入技术支持 Agent，并给出账号、验证码、网络和缓存排查步骤；但响应末尾混入了不相关的 billing Agent 内容。

5. API 调用超时
   输入：调用 API 时一直超时，请问怎么排查？
   结果：通过
   intent：technical
   agent_type：technical
   escalated：false
   knowledge_used：true
   说明：系统正确给出 DNS、网络连通性、端口、日志和 curl 复现等排查建议。回答偏长，末尾可能被截断。

6. 转人工
   输入：这个问题我希望转人工客服处理。
   结果：通过
   intent：escalation
   agent_type：general
   escalated：true
   knowledge_used：true
   说明：系统正确进入人工升级流程，并在转接前收集问题类别，减少用户重复描述。

四、总体结论
- 六个场景均成功返回 HTTP 响应，模型调用、知识库检索、Agent 路由和人工升级链路已打通。
- 完全符合预期的场景：普通咨询、重复扣款、API 超时、转人工。
- 部分符合预期的场景：退款申请、登录认证失败。

五、待优化问题
1. 退款申请未稳定路由到 billing Agent，需要增强退款、退费、账单等关键词及意图权重。
2. 登录场景出现多 Agent 响应串联，需要检查编排器的候选 Agent 合并逻辑，确保仅返回主 Agent 回复。
3. 技术排查回答过长，需要限制单次输出长度，并采用“先给关键三步，再根据反馈继续”的交互方式。

六、下一步计划
1. 优化意图识别与 Agent 路由规则。
2. 修复多 Agent 响应串联问题。
3. 启动 Vue 前端并联调 /chat 接口。
4. 增加测试用例、评测数据和演示脚本，用于秋招项目展示。

十四、可靠性与可观测性第八阶段验证
1. 每个 HTTP 请求会生成或回传 trace_id，并在响应头 X-Trace-ID、/chat 响应、阶段日志和人工工单中形成同一条可检索链路。
2. /metrics 现提供 sakikomind_http_requests_total、sakikomind_http_request_duration_seconds、sakikomind_chat_stage_duration_seconds、sakikomind_chat_stage_failures_total、sakikomind_profile_update_attempts_total 和 sakikomind_profile_update_failures_total 等 Prometheus 指标。
3. 对话主链路已按 memory_read、rag、agent、memory_write 分阶段记录成功/失败耗时；指标只使用固定阶段名和路由模板，避免把用户 ID、工单号等动态值写入标签。
4. RAG 的查询改写和结果重排均设置 RAG_LLM_TIMEOUT_S 超时（默认 8 秒）；超时时查询改写保留原问题，重排改为按确定性分数排序，不阻塞整个聊天请求。
5. 监控告警改为同一指标异常期间只生成一条；数值恢复后自动标记 resolved 并记录 resolved_at，/monitor 同时返回 active_alerts 与 recent_alerts。
6. 异步用户画像更新在 HTTP 响应后执行，失败会记录日志和 Prometheus 指标，并最多重试 2 次，因此不会拖慢本次客服回答。
7. 验收环境：Docker Compose 全部五个服务 healthy/running；/health 返回 status=ok；/monitor 返回 agent_stats、tool_stats、active_alerts、recent_alerts、suggestions；/metrics 可发现上述指标并回传 X-Trace-ID。
8. 新增 tests/test_monitor_alerts.py、tests/test_rag_timeouts.py、tests/test_profile_update.py，并扩展 tests/test_api_tracing.py。执行 docker compose exec -T sakikomind python -m unittest discover -s tests -v：27 项全部通过。
